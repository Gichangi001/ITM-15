**Two real bugs found and fixed via live testing, not just `pnpm verify`:**
1. **Next.js 16 middleware/proxy rename.** A file named `middleware.ts` (the pre-16 convention) compiles cleanly, typechecks, and even appears as `ƒ Proxy (Middleware)` in `next build` output — but is silently never invoked at runtime in this version. The exported function must be named `proxy`, not `middleware`, and — specific to this project's `src/app/` layout — the file must live at `src/proxy.ts`, not root-level `proxy.ts` (a root-level file also compiles and bundles but never gets registered). There is now nothing standing between "typed an email" and "signed in as that email" for a non-admin account — no password, no click-through, no code. Anyone who knows or correctly guesses a colleague's email can open that colleague's account. This is accepted, per the product owner's explicit and repeated instruction, on the basis that this is an internal company event game — visible game progress, mission submissions, leaderboard position — not a system holding money, health data, or anything with real-world consequence if impersonated. The blast radius is kept as narrow as the requirement allows: `checkLoginMethod` still independently gates which accounts this path can ever reach (never an admin-surface one — `instantJoin` re-checks this itself too, not just trusting the UI), and a brand-new account is still always created with exactly one hardcoded role, `PLAYER`. **If this trade-off turns out to be wrong once real participants are using it, the fix is re-adding a real verification step to `instantJoin` (a password, a code the user actually types, anything) — not something to silently reverse without being asked, for the same reason silently removing it without being asked would have been wrong.**

## Phase 20 — Security review: BLOCK, 3 findings, all fixed and re-verified (2026-09-14)

The dispatched `security-reviewer` subagent (see the section above) returned **BLOCK**, not PASS — read the actual code across every file touched by Phases 15/17(completion)/18/19, and found three real, previously-undisclosed problems. All three were fixed the same session; none were dismissed or argued away.

**CRITICAL — unlimited point farming.** Neither `submitAnswer`'s auto-grade path (`src/app/(player)/play/mission/[missionId]/actions.ts`) nor `moderateSubmission`'s approval path (`src/app/admin/submissions/actions.ts`) ever checked whether a player already had an `APPROVED` submission for a specific challenge before awarding points again — `missions.max_attempts` only capped how many *tries* existed, never how many times a correct one *paid*. For any mission where an admin didn't manually set a cap (the default is unlimited), a player who knew the correct answer could resubmit it indefinitely and be paid full points — including Unity Points — every single time, with a trivial scripted request loop and no special access. The identical root cause let a player submit the same FREE_TEXT/PHOTO_UPLOAD challenge multiple times and have a moderator's separate approvals each pay out again. This directly violated Product Guide §33.3's explicit acceptance test ("Duplicate completion does not double-pay unless configured") and this project's own "browser cannot forge points" non-negotiable — a real, live game-integrity hole, not a theoretical one.

Fixed: both paths now query for an existing `APPROVED` submission for that `challenge_id`+`player_id` before awarding, and skip the `score_events` insert (while still recording/moderating the submission itself, for a real audit trail) if one already exists. **Verified live against the real database**: a SINGLE_CHOICE mission with `max_attempts: null` answered correctly 3 times across separate requests produced exactly one 100-point `score_events` row; two separately-submitted FREE_TEXT `PENDING` submissions for the same challenge, both approved by a real admin through the real `/admin/submissions` UI, produced exactly one 50-point row (the second approval correctly updated the submission's own status to `APPROVED` without paying again).

**HIGH — email PII disclosure, directly enabled by this session's own self-registration work.** `getPlayerLeaderboard` (`src/lib/scoring/leaderboard.ts`), the leaderboards page's "Newest members" list, and the gallery's photo-attribution helper all fell back to a player's raw `email` as a display name whenever `full_name` was unset. Self-registration (`instantJoin`) creates exactly that state for every brand-new account, before onboarding fills in a name. Combined: an anonymous visitor types any email into the instant-join form, completes their own trivial onboarding, then reads that email back in plaintext on `/leaderboards` — visible to every other signed-in player, with no rate limit (before the fix below) to slow down harvesting many at once. A `awardBonusPoints` call to a not-yet-onboarded player would have put the same leak on the fully public, unauthenticated `/screen`.

Fixed: no code path that a non-owner can see now falls back to `email` — a generic "A player"/"A new player" instead; the "Newest members" query now filters to `onboarding_completed = true` so an un-named account doesn't appear there at all. **Verified live**: a freshly self-registered, deliberately-not-onboarded account's email does not appear anywhere on `/leaderboards` when viewed as a different signed-in player, and the account correctly doesn't appear in "Newest members" until it completes onboarding.

**MEDIUM — no rate limiting anywhere on the new auth surface.** `checkLoginMethod` was a free, unauthenticated oracle: call it with enough different emails and learn exactly which ones hold an admin-surface role, no friction, no limit. `instantJoin` could mint an unlimited number of real `auth.users` rows for arbitrary emails. Neither was rate-limited — confirmed no rate-limiting code existed anywhere in this repo before this fix.

Fixed with `src/lib/security/rateLimit.ts` (new) + `supabase/migrations/20260914000000_login_rate_limiting.sql` (new `login_rate_limit_hits` table, IP-keyed, self-pruning) — a real Postgres-backed limiter, not a TODO, matching this app's existing pattern of putting every integrity backstop in the database rather than reaching for new infrastructure. `checkLoginMethod` fails safe when limited (returns `"instant"`, the answer that reveals nothing, rather than erroring); `instantJoin` refuses outright with a clear message. **Verified live**: pre-seeding hits past the configured threshold for the test client's own IP correctly made a real admin email resolve to the non-admin branch on the next check, exactly the fail-safe behavior intended.

**LOW/informational, fixed anyway though the reviewer offered documentation as an acceptable alternative**: a comment on the `notifications` "players can update read_at on their own notifications" RLS policy (`supabase/migrations/20260913100000_admin_notifications.sql`) claimed the policy restricted which *column* could change — RLS is row-level, not column-level, so that was never true (a player can PATCH other columns on their own notification row via direct REST, just never another player's row). Corrected the comment to say so plainly, with the confirmed self-only blast radius as the explicit reason a trigger wasn't judged necessary. Also added `.toLowerCase()` email normalization to the schema this session's login work introduced (a data-hygiene gap, not independently exploitable since Supabase Auth already normalizes case at the `auth.users` level).

`pnpm verify` (lint/typecheck/104 tests/build) clean after the fix commit; `get_advisors` (security) shows no new findings beyond the pre-existing, already-disclosed deny-all-by-design ones. All test accounts/data created to verify these fixes were deleted afterward.
